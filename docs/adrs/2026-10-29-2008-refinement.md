# Correctness means refinement of observable behaviour

Status: accepted; refined by ADR-2026-10-30-0816

## Context

This is decision S4 of the fir v0 decision record, agreed on 2026-10-29 and
stated in the M0 epic ([#5](https://github.com/pmatos/funk/issues/5)).

Funk checks its hand-written Rust, such as backends, against the Lean
semantics. That needs one precise meaning of "this target is correct for this
source". Source and target need not behave identically: where the source has
UB or poison, the target is free to do more than one thing.

## Decision

- A target is correct if each of its observable behaviours is allowed by the
  source.
- Source UB allows anything.
- A poison result is refined by any value.
- Refinement is defined over a domain of observations that the semantics
  supplies, not hard-wired to integer return values. Each dialect supplies its
  observations (G0, ADR-2026-10-29-2016).

In M0, a function's observable behaviour is its return value, UB, or
non-termination (fuel exhausted). The full definition also counts calls to
external symbols and reachable memory. M0 has no memory, and every M0 callee
is inside the module. The one exception is the `i128` division helper, which
is tested on its own.

## Consequences

- The differential harness compares a native result with the `fir-ref` result
  by refinement. A poison result from `fir-ref` matches any native value. A
  test whose `fir-ref` result is UB is invalid, never a pass.
- `freeze` makes the source's behaviour a set of outcomes. ADR-2026-10-29-2017
  says how the harness checks a native result against that set.
- Any later check, such as per-compile refinement checking (S8, not decided),
  checks this relation and no other.
- When memory and external calls arrive, observable behaviour grows to cover
  them, and the relation stays the same.
