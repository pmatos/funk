# fir must be able to reach any kind of hardware

Status: accepted; refined by ADR-2026-10-30-1146

## Context

This is ground rule G0, set by the human on 2026-10-29, after the other rows
of the fir v0 decision record. The roadmap states it, and the M0 epic
([#5](https://github.com/pmatos/funk/issues/5), table and
[comment](https://github.com/pmatos/funk/issues/5#issuecomment-6505395072))
spells out what it asks.

Funk is a reusable toolchain, in the spirit of LLVM. Its users will target
more than CPUs. Structures fixed early, such as a closed list of ops or a
grammar with one production per op, are costly to open once code depends on
them.

## Decision

- fir must be able to reach any kind of hardware: CPUs first, but also GPUs,
  NPUs, TPUs and hardware we cannot predict yet, such as photonic or quantum
  processors.
- The core stays a small CPU-shaped dialect. Other targets come in as
  extension dialects. The openness lives in how fir is built, not in what the
  core contains.
- G0 is a standing check. Every decision, now and later, is checked against
  it, and none may close that door.

### What G0 means for the decided rows

- **E0** (ADR-2026-10-29-2005) binds the core dialect only. Extensions may
  define other region kinds later, such as unordered dataflow regions.
- **Types and ops come from dialects**, so there is no closed core enum. The
  core's types (`iN` and the reserved `ptr`) are one dialect's types, not the
  whole type system.
- **Refinement** (S4, ADR-2026-10-29-2008) is defined over a domain of
  observations that each dialect supplies.
- **Symbol tables can nest** (H2 and H3, ADR-2026-10-29-2011 and
  ADR-2026-10-29-2012), for example a device module inside a host module. M0
  does not use nested modules, but its data structures must not rule them
  out.
- **One text grammar covers every dialect** (P3, ADR-2026-10-29-2014).

### What G0 asks of M0

- **Rust IR.** `funk-ir` represents an op generically: a name, operands,
  attributes, result types, regions and a location, checked through an op
  registry in which each dialect registers its ops. It is not a closed Rust
  `enum` of core ops. Types are extensible the same way.
- **Lean semantics.** It is parameterized over the dialect. Ops, types and
  effects come in through typeclasses, in the style of LeanMLIR, not as one
  closed `inductive`. Whether fir builds on LeanMLIR itself is the question of
  the spike in [#24](https://github.com/pmatos/funk/issues/24), not this ADR.
- **Text format.** It uses one grammar for every op (name, operands,
  attributes, regions and types), so a new dialect needs no parser change.

[#8](https://github.com/pmatos/funk/issues/8),
[#9](https://github.com/pmatos/funk/issues/9) and
[#10](https://github.com/pmatos/funk/issues/10) build these structures and
record their details.

### What the open decisions inherit

These decisions stay open. G0 only constrains them:

- The memory model (S3) needs several memories and address spaces.
- Dialects and extensions (H4) must let extensions add types and attributes,
  not only ops.
- The verifier will need a hook for use-once (linear) values, which quantum
  dialects require.

## Consequences

- M0 builds more structure than a closed core would need: a registry, a
  parameterized semantics and a generic grammar.
- Checks that a closed Rust `enum` would give for free, such as an op's
  operand count, move into the registry and the verifier.
- Lean proofs, such as the round-trip theorem, are stated over the dialect
  parameter where they can be, so a new dialect does not reopen them.
- Every later decision, including the open ones above, is checked against G0.
- No milestone targets non-CPU hardware yet; G0 keeps the door open, and the
  roadmap lists that as an open gap.
